# Fidelity audit: pi-mstack frozen snapshot

Verdict: **ISSUES**

Snapshot identifier: SHA256 of `SNAPSHOT.sha256` is `62b285c5d2ffe0e66b97cc32ff2309d4473633a453bb004dabcef837513a5bc2`, matching the brief. I verified `sha256sum -c SNAPSHOT.sha256` passes for all listed files, and there is no Git HEAD in scope. This is an early audit, not final acceptance. Principles that shaped the audit, from the Poteto Mode leaf I read: Prove It Works (I ran the snapshot's own check instead of trusting file presence) and Sequence Work into Verifiable Units / Build the Lever (source accounting and generator checks are the right first unit, and the failures below are exactly in that unit).

## Blockers

1. **The shipped acceptance digest is stale, so the package's own check fails.** `upstream/acceptance.json:2` records reviewDigest `f826b6ce…7624`, but `digest()` over the current manifest plus `tools/` and `port/` inputs (`tools/importer.mjs:85-88`) computes `72e7dcfa…b804`. Running `node tools/upstream.mjs check` in the snapshot exits 1 with "Adaptation inputs changed or acceptance invalid" at `tools/importer.mjs:170`. Either a `tools/`/`port/` input or the manifest changed after acceptance, or acceptance was never regenerated after a fix. Smallest fix: review what changed since acceptance, then re-run propose/accept with the new reviewed digest; do not hand-edit `acceptance.json`, since that would defeat the gate the digest exists to enforce (`docs/design.md`, "Import and update contract").

2. **`generated/index.sha256` is missing, so the generated tree is not the output of the current generator.** `generate()` always emits both `index.json` and `index.sha256` (`tools/importer.mjs:173-174`), and the manual-drift guard reads `index.sha256` unconditionally (`tools/importer.mjs:184`), which would throw ENOENT once blocker 1 is fixed and regeneration is attempted against this tree. All 539 indexed generated files do match `generated/index.json` hashes, and no unindexed files are present, so this looks like a partially published or hand-pruned tree rather than content drift. Smallest fix: after blocker 1, run `npm run generate` (with explicit `repair generated` if the drift guard demands it) and confirm both index files exist. Note `npm pack --dry-run` confirms the tarball currently also lacks `generated/index.sha256`.

## Issues (non-blocking but real)

3. **The host-term scanner classifies only known terms; it cannot emit unknown terms.** `tools/render.mjs:49-50` records which mapping patterns matched, and `tools/render.mjs:24-25` only checks that every key in the hand-maintained `port/required-terms.json` has a mapping. Nothing scans for host vocabulary outside the registry, contrary to the design ("The scanner emits unmapped terms… Missing mappings or roles fail generation"). Concrete survivor: `subagent_type` is not a mapping key or pattern, yet it appears in active prose at `generated/skills/poteto-mode/SKILL.md:100`, `generated/skills/reflect/SKILL.md:29`, and `generated/skills/no-comments/SKILL.md:23`. The Pi adapter preamble tells readers mappings take precedence, so these are interpretable, but a future upstream term will pass silently. Smallest fix: add a denylist/unknown-term pass over a term inventory (starting with `subagent_type`) that fails generation on unclassified matches in adapt-disposition Markdown, with an allowlist for fixtures and preserved files.

4. **Lock repair stores process-start evidence but never verifies it.** `acquireLock` records `start` via `ps lstart` (`tools/importer.mjs:90-97`), but `repairLock` (`tools/importer.mjs:103-115`) decides deadness from PID existence alone. PID reuse by an unrelated live process fails safe (it blocks), so this is not a safety hole, but the stored start evidence is decorative and a reused-but-dead PID check cannot distinguish the recorded owner. Also, a crash between `mkdirSync` and writing `owner.json` leaves a lock whose repair path throws a raw ENOENT from `readJSON` instead of the ambiguous-lock acknowledgment flow. Smallest fix: compare current `lstart` for the PID against `owner.start` before declaring a live owner, and treat a missing `owner.json` as ambiguous (token acknowledgment impossible, so require operator removal with an explicit message).

5. **Role-reference scanning is narrower than the design promises.** `tools/render.mjs:15-18` only catches roles written as `` `name` line `` or `` `name` role ``. References in other shapes (for example "`swarm workers` model") are unchecked, so a renamed or mistyped role in that shape would not fail generation. The 17-role registry itself is currently exact: I verified `port/roles.json` matches the labels declared in upstream `skills/setup-pstack/SKILL.md`, all 17 names appear in upstream prose, and the four panel roles are flagged. Smallest fix: extend the reference pattern to backticked known-label-shaped phrases followed by model/selector wording, or scan all backticked spans against a label grammar.
